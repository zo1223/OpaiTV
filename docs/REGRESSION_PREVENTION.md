# 回归预防与经验沉淀

本文记录可复用的工程经验，用于减少“修改 A、破坏 B”的跨功能回归。它是 `AGENTS.md` 的补充说明，不是需求、计划或当前行为的权威来源；实际行为始终以代码、测试和构建结果为准。

## 1. 回归为什么发生

跨功能回归通常不是两个功能真的毫无关系，而是它们共享了未显式记录的契约，例如：

- 同一份状态、缓存、配置或持久化数据。
- 同一个事件、回调、导航生命周期或外部进程。
- “只会执行一次”“每次都会重新通知”“对象每次都会重建”等未经验证的假设。
- 单元测试只覆盖函数结果，没有覆盖首次执行之后的切换、复用、重试或退出流程。
- 多项功能混在同一批改动中，无法及时判断是哪项修改改变了既有行为。

预防重点不是要求开发者或 AI 更加小心，而是把隐式契约变成检查项，把已发生的故障变成可重复验证的场景。

## 2. 修改前的最小影响分析

中高风险修改开始前，用几行文字确认以下内容即可，不需要为小任务创建正式计划文件：

```text
目标：要改变什么行为
直接影响：修改的模块、状态和调用路径
共享契约：事件、生命周期、配置、缓存、外部依赖
保持不变：用户已经依赖的相邻行为
验证：原始场景、相邻场景、发布产物检查
```

出现下列信号时，应扩大验证范围：

- 修改公共接口、共享模型或全局设置。
- 新增或改变状态门控、遮罩、等待条件、超时或重试。
- 复用播放器、网络连接、进程、窗口、缓存或单例服务。
- 改变配置路径、序列化字段、安装目录或升级流程。
- 一次修改跨越多个页面、服务或项目。

## 3. 分层验证门槛

验证应与风险匹配，但每一层都要证明具体行为，而不是只报告测试数量。

1. 定向测试：直接覆盖本次修改和原始症状。
2. 相邻流程测试：覆盖共享状态的上游和下游，以及第二次执行、切换、重试和取消。
3. 完整测试：触及公共契约、持久化、导航、播放器或打包流程时执行。
4. 集成验证：涉及 mpv、LibVLC、网络、文件系统、安装器等真实依赖时执行。
5. 发布产物冒烟：从 `desktop\publish\win-x64-self-contained` 启动最终 EXE；安装器或更新逻辑变化时同时验证安装包和校验文件。

Bug 修复优先增加“修复前失败、修复后通过”的测试。真实依赖无法稳定进入 CI 时，至少保留可重复命令、固定样本或协议事件序列测试，并在交接中说明自动化缺口。

## 4. 项目关键回归矩阵

| 改动区域 | 最少应验证的行为 |
| --- | --- |
| 本地播放器 | 首次播放、同一引擎第二次加载、切集、重试、拖动进度、断点续播、停止后重开、窗口与全屏切换 |
| 在线播放与换源 | 搜索、详情、源解析、首次播放、换源、失败回退、历史记录对应关系 |
| 播放记录与缓存 | 首次保存、定时更新、续播、切集、换源后迁移、失败或取消时不覆盖有效记录 |
| 设置与视频源 | 新增、编辑、删除、重启后读取；更新安装前后自定义视频源和其他用户配置保持不变 |
| 更新功能 | 版本比较、Release 资产匹配、下载、SHA-256 校验、取消和失败处理、更新安装后重新启动 |
| 桌面打包 | 标准发布目录 EXE 启动、内置 mpv/LibVLC/代理文件存在、安装包生成、校验文件匹配 |
| 导航与快捷键 | 进入和退出页面、返回栈、重复进入、全屏退出、焦点和快捷键不触发重复操作 |

只需执行与改动相关的行；修改共享模型或跨模块契约时，应扩大到所有受影响行。

## 5. 事件驱动与外部进程规则

外部系统的事件通常表示“值发生了变化”，不等于“每次业务操作都会报告一次当前值”。因此：

- 本地状态被重置后，先判断外部真实状态是否也发生了变化。
- 如果正确性依赖当前值，应在合适的生命周期节点主动查询，而不是无限等待变化事件。
- 异步请求要带唯一请求标识或播放代次，旧操作返回后不得覆盖新状态。
- 等待画面、网络或进程响应时必须有超时、状态校准或明确失败路径，不能永久停留在加载状态。
- 测试至少覆盖首次调用和复用同一对象后的第二次调用；仅测试冷启动不足以证明生命周期正确。

## 6. 2026-07-27：本地视频有声音但无画面

### 现象

本地视频已经播放，有声音且时间进度持续变化，但界面一直显示“正在等待画面”。

### 引入改动

为了避免首帧出现前暴露原生黑色窗口，播放器增加了首帧门控：本地 mpv 宿主先保持隐藏，收到视频输出就绪信号后再显示，并关闭加载遮罩。

### 错误假设

应用在每次 `SwitchToAsync` 时把 `HasVideoOutput` 重置为 `false`，并假设 mpv 每次 `loadfile` 都会重新发送 `vo-configured=true`。

mpv 进程实际会被复用。首次播放时属性从 `false` 变为 `true`，会发送变化事件；再次加载时该属性可能一直为 `true`，没有发生变化，因此不会再次发送事件。应用自己的状态已经被清空，却收不到新的通知，导致窗口永久隐藏。音频和进度不依赖这个 UI 门控，所以仍然正常。

### 为什么原测试没有发现

- 只验证了启动参数和首次播放相关行为。
- 没有验证同一 mpv 进程连续执行两次 `SwitchToAsync`。
- 测试关注事件能否被解析，没有验证“本地状态重置、外部状态未变化”的组合。

### 修复方式

- 继续监听 `vo-configured` 的变化事件。
- 每次收到 `file-loaded` 后，主动查询当前 `vo-configured` 状态。
- 查询携带唯一 `request_id`，并与当前播放代次匹配，避免旧响应污染新播放。
- 保留首帧门控，但不再把单一变化事件作为解除等待的唯一依据。

相关实现：

- `desktop/OrionTV.Desktop.App/LocalPlayback/MpvLocalEngine.cs`
- `desktop/OrionTV.Desktop.App/Views/PlayerView.xaml.cs`
- `desktop/OrionTV.Desktop.Tests/MpvLocalEngineTests.cs`

### 永久检查项

- 使用同一 `MpvLocalEngine` 连续加载两次视频，两次都必须得到视频输出状态。
- 初始隐藏和可见宿主两种情况下都验证第二次加载。
- 验证音频和时间在推进时，UI 不会因缺失的重复事件永久等待。
- 后续修改首帧、切集、重试或窗口显示逻辑时，重新执行本节场景。

## 7. 新增经验的统一模板

只有经验具有跨任务复用价值，或用户明确要求沉淀时，才追加到本文；不要把普通执行日志全部写进来。

```markdown
## YYYY-MM-DD：问题标题

### 现象
用户可观察到的失败行为。

### 引入改动
原本要解决什么问题，改变了哪些契约。

### 错误假设
哪个隐式前提与真实运行行为不符。

### 为什么原测试没有发现
缺失了哪个状态、边界或真实依赖场景。

### 修复方式
修复了什么契约，如何隔离旧状态或失败路径。

### 永久检查项
以后哪些修改必须执行哪些可重复验证。
```
